2. `college.trg_Students_AverageGradeAudit` срабатывает AFTER UPDATE. Старые значения берёт из deleted, новые — из inserted, сопоставляет строки по id. Неизменившиеся значения не журналируются.
3. Проверено изменение балла студента id=1 на 4,8; добавляется одна запись аудита.

5. `college.trg_Students_ValidateGrade` срабатывает AFTER INSERT, UPDATE. При наличии хотя бы одной строки с баллом вне 0–5 выполняет THROW 51008.
6. Проверены допустимый балл 4,5 и отклонение балла 6. После отклонения проверяются исходный балл и отсутствие новых записей аудита. Дополнительно проверён INSERT с баллом −1.
7. События и данные триггеров разобраны ниже.

В итоговой части в журнал добавлены old_age и new_age, а триггер аудита изменён для отслеживания и возраста, и балла. Изменение обоих полей одной строки создаёт одну запись с обоими старыми и новыми значениями. Проверены также изменение только возраста и UPDATE без фактических изменений.

## Разбор работы триггеров

| Триггер | Событие | Используемые данные |
|---|---|---|
| trg_Students_AverageGradeAudit | AFTER UPDATE | deleted — старые значения; inserted — новые |
| trg_Students_ValidateGrade | AFTER INSERT, UPDATE | inserted — значения, проверяемые перед завершением операции |

При UPDATE нужны обе таблицы, чтобы сравнить предыдущее и новое состояние одной и той же строки. SQL Server вызывает DML-триггер для оператора, а не отдельно для каждой изменённой строки. Поэтому аудит использует INSERT…SELECT с JOIN, а проверка — EXISTS по всему набору inserted. Результат не зависит от порядка выполнения двух AFTER-триггеров: ошибка проверки откатывает и изменение студентов, и аудит в общей транзакции.

## Ответы на вопросы для самопроверки

1. **DML-триггер** — объект базы, автоматически реагирующий на INSERT, UPDATE или DELETE таблицы либо представления.
2. **Когда срабатывает:** при соответствующем событии оператора. Даже если оператор не изменил строк, триггер может быть вызван, поэтому его код должен обрабатывать пустые наборы.
3. **AFTER и INSTEAD OF:** AFTER выполняется после успешного выполнения изменения и проверки ограничений; INSTEAD OF заменяет исходную операцию своей логикой.
4. **inserted** — логическая таблица новых строк для INSERT или новых версий строк для UPDATE.
5. **deleted** — логическая таблица удалённых строк для DELETE или старых версий строк для UPDATE.
6. **inserted при UPDATE:** новые значения всех строк, затронутых оператором.
7. **deleted при UPDATE:** значения тех же строк до изменения.
8. **Несколько строк в inserted:** да, например при обновлении всей группы или INSERT…SELECT.
9. **Почему нельзя рассчитывать на одну строку:** выбор одного значения потеряет часть обновлений и сделает аудит или проверку неверными для массового оператора.
10. **Применение:** аудит изменений, сложные межтабличные бизнес-правила, автоматическая реакция на изменение данных.
11. **Отличие от процедуры:** процедуру вызывают явно через EXEC; триггер запускается автоматически при заданном событии и работает в транзакции вызывающего оператора.
12. **Когда лучше CHECK или другое ограничение:** для простого диапазона значений предпочтителен CHECK, для обязательности — NOT NULL, для уникальности — UNIQUE, для ссылочной целостности — FOREIGN KEY. Здесь диапазон проверяется триггером в соответствии с заданием.

## Запуск и проверка

Используйте учебную `CollegeDB` со схемой college из [CollegeDB_dump.sql](../CollegeDB_dump.sql). Скрипт выполните целиком в SSMS; GO отделяет определения объектов от остальных команд. Он рассчитан на повторный запуск и сохраняет существующие записи журнала. Старая таблица аудита комплексной лабораторной поддерживается: возрастные столбцы добавляются при отсутствии.

Тестовые UPDATE и INSERT выполняются в транзакциях и откатываются после вывода результатов. Записи аудита этих тестов тоже откатываются; пустой журнал после завершения не означает, что триггер не работал. Пропуски в счётчиках IDENTITY после отката нормальны. Определения триггеров и столбцы таблицы сохраняются.
