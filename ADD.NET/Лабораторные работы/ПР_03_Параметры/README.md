# Практическая работа №3 — Параметризованные SQL-запросы

Выполнил: **Мингазов Ахнаф**. Проект: **AdoNetPractice03**.

Выполнены задания 1–9, самостоятельное меню и дополнительное задание. Пункты 1–5: поиск по ID, поиск по точному названию, добавление, изменение цены, удаление. Пункт 6 выводит товары с ценой от заданной, пункт 7 получает их количество через ExecuteScalar, пункт 8 ищет клиентов по части ФИО через LIKE.

Пользовательские значения передаются через SqlParameter. SELECT использует ExecuteReader; изменение — ExecuteNonQuery. В Catalog.AddProduct явно заданы NVarChar(150), Int, Decimal(10,2), Precision и Scale.

## Ответы по сравнению двух подходов

1. При конкатенации пользовательское значение находится непосредственно в SQL-строке внутри кавычек.
2. При параметризации SQL содержит @name, а само значение хранится отдельно в Parameters.
3. Параметр безопаснее, потому что значение обрабатывается как данные, а не дополнительный SQL-код. Ввод `' OR 1=1--` ищется как буквальное название.
4. Конкатенация смешивает код и данные; параметризация сохраняет структуру запроса отдельно от значений.

AddWithValue выводит SQL-тип из значения C#. Явное указание SqlDbType, длины, Precision и Scale позволяет точно согласовать параметры со схемой БД. Поэтому дополнительное задание выполнено с явно типизированными параметрами.

Проверка: ID 1 и отсутствующий 999999; название «Капучино» и строка с SQL-синтаксисом; порог 200 — два товара на исходном наборе; поиск «Иван». Добавьте отдельный тестовый товар, измените его цену и удалите именно его ID. Для отсутствующего ID UPDATE/DELETE возвращает 0. Внешние ключи запрещают удалять товары из существующих позиций заказов.

**Вывод:** параметры отделяют данные от SQL, проверка ввода дополняет этот механизм.
