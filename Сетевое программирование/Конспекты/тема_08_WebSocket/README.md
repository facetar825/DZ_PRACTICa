# WebSocket и обмен в реальном времени

WebSocket поддерживает длительное двустороннее соединение. После установки канала сервер может отправлять сообщения по собственной инициативе. При polling клиент периодически создаёт HTTP-запросы, даже если обновлений нет.

В классическом HTTP/1.1-сценарии клиент отправляет Upgrade: websocket и служебные Sec-WebSocket-заголовки. Ответ 101 Switching Protocols подтверждает смену протокола. Далее канал передаёт WebSocket-фреймы. ws использует незашифрованный канал, wss защищает его через TLS.

Сообщение может включать несколько фреймов. Библиотека собирает их в целое сообщение, поэтому обработчик message отличается от data на обычном TCP-сокете. Формат содержимого определяет приложение. Текст и двоичные данные поддерживаются независимо от JSON.

Состояния клиента — CONNECTING (0), OPEN (1), CLOSING (2), CLOSED (3). Отправка допустима после open. Событие message доставляет сообщение, error уведомляет об ошибке, close содержит итоговый код и причину завершения.

close начинает обмен Close-фреймами. terminate в ws принудительно обрывает соединение. Управляющие Ping/Pong проверяют активность, а строка PING в echo-примере остаётся прикладным текстом. В браузере API не даёт вручную отправлять протокольный Ping.

Для устойчивости нужны ограничение maxPayload, проверка входных данных и Origin, обработчики error и close. В интерфейсе пользовательский текст выводят через textContent. В реальной системе дополнительно нужны wss и проверка прав доступа. Event Loop продолжает обслуживать сообщения всех подключений, поэтому тяжёлые синхронные расчёты задерживают их.
