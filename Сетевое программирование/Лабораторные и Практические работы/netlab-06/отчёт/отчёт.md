# Практическая работа №6

## Unicast, Broadcast и Multicast в UDP

**Цель:** на практике сравнить способы доставки UDP-датаграмм, использовать `node:dgram` и подписку на multicast-группы, реализовать мини-систему оповещений NetLab Announcements.

**Среда:** Node.js v22.16.0; `node:dgram` и `node:readline`; UDP-порт `3030`; группы `239.255.10.10` и `239.255.10.11`.

## 1. Структура и реализация (задания 1–3)

```text
netlab-06/
  receiver.mjs         универсальный UDP-приёмник
  sender.mjs           UDP-отправитель (3 режима)
  tests/smoke.mjs      автоматические локальные опыты
  отчёт/               отчёт PDF, Markdown, журнал тестов
  README.md            инструкции
```

Приёмник слушает `0.0.0.0:3030`, включает `reuseAddr`, подписывается на `239.255.10.10` по умолчанию и выводит отправителя, текст, дату и время. Список групп изменяется локальной переменной `MULTICAST_GROUPS`. Отправитель принимает режим, IPv4-адрес и пользовательский текст из аргументов команды. Для Broadcast вызывается `setBroadcast(true)`. Для Multicast установлен `TTL=1` и включён loopback. Для выбора IPv4 интерфейса используется `MULTICAST_IFACE`.

## 2. Проверка Unicast (задание 4)

```powershell
# Терминал 1:
node receiver.mjs
# Терминал 2:
node sender.mjs unicast 127.0.0.1 "Привет, NetLab!"
```

В локальном автоматическом опыте приёмник получил строку `Привет, NetLab!` с адреса `127.0.0.1` и временного порта отправителя. В актуальном журнале использован текст `Проверка адресной доставки`. Если отправитель направит пакет на другой UDP-порт, слушатель порта 3030 не получит эту датаграмму.

## 3. Проверка Broadcast (задание 5)

```powershell
ipconfig
node sender.mjs broadcast 192.168.1.255 "Объявление всему классу"
```

**Важно:** адрес `192.168.1.255` годится только для конкретной сети `192.168.1.0/24`. Перед работой с учебными ПК нужно определить IPv4 и маску собственной подсети. В проведённом автоматическом опыте успешно **отправлена и получена Broadcast-датаграмма только через loopback-адрес `127.255.255.255`**. Доставка по реальному учебному IPv4-сегменту **не проверялась** и зависит от брандмауэра и сетевой инфраструктуры.

## 4. Проверка Multicast (задание 6)

```powershell
# Приёмник по умолчанию подписан на группу 1
node receiver.mjs
# Передача в группу 1
node sender.mjs multicast 239.255.10.10 "Сбор группы 1"
# После перезапуска приёмника с переменной:
$env:MULTICAST_GROUPS = "239.255.10.11"
node receiver.mjs
# Передача в группу 2 в другом терминале
node sender.mjs multicast 239.255.10.11 "Сбор группы 2"
```

В отдельном локальном тесте подтверждена доставка для каждой группы, когда приёмник подписан на неё. При подписке только на группу 1 доставка сообщения второй группы не наблюдалась. Это результаты **локальной тестовой среды**, а не нескольких реальных компьютеров учебного кабинета. На одном ПК с несколькими UDP-приёмниками поведение рассылки может различаться между ОС; чистый опыт выполняйте на раздельных учебных ПК.

## 5. Сравнение трёх режимов (задание 7)

| Критерий | Unicast | Broadcast | Multicast |
|---|---|---|---|
| Адрес назначения | Конкретный IPv4 (127.0.0.1 для теста) | Broadcast-адрес IPv4-подсети | Групповой IPv4, например 239.255.10.10 |
| Подписка на группу | Не требуется | Не требуется | Обязательна для получателей |
| Для кого предназначена датаграмма | Один адресат | Узлы широковещательного домена | Участники группы |
| Гарантирована ли доставка UDP | Нет | Нет | Нет |
| Что проверено локально | Получено на 127.0.0.1 | Получено на 127.255.255.255 (loopback) | Получено в обеих группах поочерёдно |
| Получено в учебном кабинете | Не проверялось | Не проверялось | Не проверялось |

Одна multicast-датаграмма передаётся на **групповой IP-адрес**; это не цикл отдельных `send()` по всем адресатам. Распределение подписчикам выполняется сетевым механизмом, а не кодом отправителя. Отправка сама по себе не подтверждает получение.

## 6. Самостоятельная и повышенная части (задание 8)

Выполнены пять заданий: текст из аргументов командной строки, дата и время при приёме, локальная команда `STOP`, вторая multicast-группа, рекомендация по рассылке всему классу.

**Рекомендация:** для организованной группы ПК в классе предпочтителен **Multicast**, если сеть поддерживает его, а нужные компьютеры подписаны на группу. Он адресует сообщения только участникам. Broadcast удобен при рассылке в одном широковещательном домене без подписки, но отправляет пакеты всем подходящим узлам и чаще ограничивается инфраструктурой. Для критически важных подтверждаемых сообщений нужны дополнительные подтверждения на уровне приложения, например адресный обмен.

**Повышенная сложность:** предусмотрен выбор интерфейса `MULTICAST_IFACE`; для полного опыта между двумя физическими ПК необходимо установить свои адреса интерфейсов и проверить доставку в разрешённой учебной сети. Утверждать, что это сделано на двух учебных ПК, нельзя: такая проверка не выполнялась.

**Схема движения сообщений:**

```text
                    Отправитель (преподаватель)
                  /             |              \
  Unicast 127.0.0.1      Broadcast subnet      Multicast 239.255.10.10
          |                     |                        |
   Один выбранный ПК      Все подходящие ПК      Только подписчики группы
```

## 7. Ответы на вопросы для закрепления

**1. Чем Unicast отличается от Broadcast?** Unicast адресован одному IPv4-адресу; Broadcast охватывает широковещательный домен соответствующей IPv4-сети.

**2. Для чего используется Multicast?** Для доставки одного потока/сообщения группе заинтересованных получателей, которые присоединились к соответствующему multicast-адресу.

**3. Почему multicast-адрес не равен IP отдельного компьютера?** Это логический адрес группы, а не уникальный IP сетевого интерфейса; один и тот же групповой адрес могут использовать несколько участников.

**4. Что делает `socket.addMembership()`?** Запрашивает присоединение UDP-сокета к заданной multicast-группе на подходящем сетевом интерфейсе.

**5. Зачем `setBroadcast(true)`?** Разрешает UDP-сокету посылать IPv4-датаграммы на широковещательный адрес.

**6. Почему broadcast-адрес зависит от маски?** Биты адреса за пределами сетевого префикса становятся единицами, поэтому разная длина префикса даёт разные broadcast-адреса.

**7. Гарантирует ли UDP доставку широковещательных датаграмм?** Нет; даже успешный вызов `send()` не гарантирует, что адресаты их получили.

**8. Почему на одном Wi-Fi Multicast может работать иначе, чем на Ethernet?** Беспроводная сеть может использовать изоляцию клиентов, фильтрацию и другие способы передачи широковещательных/групповых кадров, что меняет фактическую доставку.

**9. Зачем при нескольких интерфейсах выбирать нужный IPv4-адрес?** Чтобы отправка и подписка шли через интерфейс сети, в которой расположены предполагаемые получатели, а не через другой сетевой адаптер.

**10. Где это применимо в реальных локальных сетях?** Локальные объявления и поиск сервисов, групповые уведомления, потоковое распространение информации в управляемых сетях.

Подтверждена фактическая локальная доставка Unicast, Broadcast через loopback и двух Multicast-групп, а также реакция локального `STOP`. Исходный журнал находится в `отчёт/результаты-тестов.txt`.

Результаты по реальной учебной LAN нужно проверить отдельно.
